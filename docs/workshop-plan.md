# Воркшоп: Architecture as Git

**Аудитория:** аналитики, ИБ-специалист (админ GitLab)  
**Длительность:** 1.5 часа  
**Формат:** презентация + живое демо + практика

---

## Часть 1. Проблема и подход (20 мин)

### Проблема
- Архитектурные схемы в draw.io / Visio / Confluence — не версионируются
- Непонятно кто, когда и зачем изменил схему
- Схемы устаревают через неделю после создания
- Нет связи между бизнес-функцией и конкретным API/таблицей

### Подход
- ArchiMate — стандарт моделирования корпоративной архитектуры
- Archi — бесплатный инструмент (open-source)
- coArchi — совместная работа через Git (знакомый инструмент)
- jArchi — скриптинг (автоматизация рутины)

### Для ИБ
- Модель лежит в GitLab под контролем ИБ
- Каждое изменение = коммит с автором и датой
- Бесплатный аудит архитектурных изменений

## Часть 2. Живое демо (40 мин)

### Демо 1: Git для архитектуры (10 мин)
1. Открыть GitHub/GitLab → показать репозиторий
2. Показать историю коммитов: «вот кто и когда что менял»
3. Показать diff: «вот что именно изменилось в архитектуре»
4. Открыть Archi → Collaboration → Pull → изменения подтянулись

**Вау-момент:** архитектура версионируется как код. Знакомый Git, только вместо кода — архитектурные решения.

### Демо 2: Импорт БД в модель (15 мин)
1. Показать DDL-файл `ckd-database.sql` — 16 таблиц, 6 схем
2. Запустить jArchi-скрипт `import-ddl-to-archimate.ajs`
3. На глазах аудитории из SQL появляются Data Objects в модели
4. Показать Properties: колонки, типы, PK, NOT NULL
5. Показать FK → Association relationships

**Вау-момент:** из SQL-файла за 10 секунд — полная модель данных в архитектуре. Со связями.

### Демо 3: От бизнеса до кода за 10 секунд (15 мин)
1. Показать бизнес-сервис «Передача данных в ERP»
2. → модуль, который его реализует
3. → Application Interface
4. Кликнуть → открывается Swagger в браузере
5. → конкретный endpoint `POST /land-plots/export`

**Вау-момент:** полная трассируемость от бизнеса до API. Вопрос «зачем нам это» больше не возникает.

## Часть 3. Практика (20 мин)

1. Коллеги устанавливают Archi + coArchi (если заранее не установлено)
2. Подключаются к репозиторию через Collaboration → Import Remote Model
3. Открывают модель, навигируют по View
4. Добавляют один элемент (например, новый Application Interface)
5. Делают Publish (коммит) с осмысленным сообщением
6. Смотрят как изменение появляется у соседа после Pull

---

## Часть 4. Q&A и следующие шаги (10 мин)

### Ожидаемые вопросы
- «А если конфликт мержа?» → coArchi разрешает на уровне XML-элементов, не строк
- «А Sparx EA?» → Archi → Sparx EA — естественный путь по мере зрелости
- «А кто будет поддерживать модель?» → все, кто делает изменения. Git = распределённая ответственность

### Следующие шаги
1. Создать репозиторий в корпоративном GitLab
2. Перенести модель ЦКД
3. Договориться о конвенциях именования
4. Начать фиксировать архитектурные решения как коммиты
